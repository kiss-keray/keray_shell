# 备份、恢复与演练

“命令成功”“存在快照”“文件能列出”都不等于可恢复。备份与恢复必须围绕业务数据一致性、RPO、RTO 和实际恢复验证设计。

## 1. 先定义恢复目标

开始前明确：

- **范围**：主机、文件、数据库、volume、配置、密钥、系统状态还是整机。
- **RPO**：最多可接受丢失多久的数据。
- **RTO**：从事故到恢复服务最多多久。
- **一致性**：crash-consistent、filesystem-consistent 还是 application-consistent。
- **恢复点**：时间、版本、事务位置和时区。
- **恢复位置**：隔离环境、新主机、新路径还是原位覆盖。
- **依赖**：加密密钥、软件版本、schema、外部对象存储、DNS、证书和账号。

无法回答这些问题时，只做盘点和计划，不执行覆盖性恢复。

## 2. 备份资产盘点

记录：

- 备份工具、配置的权威来源和负责团队。
- 最近成功时间、持续时间、大小、保留策略和失败告警。
- 全量/增量/差异链及其依赖是否齐全。
- 存储位置、不可变/离线副本、跨账户/跨区域副本。
- 加密方式、密钥位置、访问审计和灾难时的密钥恢复流程。
- 最近一次真实恢复演练时间与结果。

查看备份目录或工具状态可能暴露客户名、路径和对象标识，按 R1 限定输出。不要把 secret、访问 URL 签名或密钥展示到聊天。

## 3. 快照与同步副本的边界

- 文件系统/LVM/云盘快照通常只保证块设备时间点状态，未必保证数据库和跨卷一致性。
- RAID 是可用性机制，不是备份；误删、损坏和勒索可能同步到所有成员。
- `rsync` 镜像、复制目录和双机同步可能同步删除或损坏，也不自动具备历史版本。
- 容器镜像不包含未烘焙的 volume 数据；volume 快照也不包含镜像/配置/secret。
- btrfs/ZFS/LVM 本地快照与源共享故障域，不应是唯一副本。

在声称“有备份”前必须说明恢复依赖和已验证程度。

## 4. 创建备份的安全条件

创建或调整生产备份是 R2；冻结应用、数据库锁、LVM/云盘快照、挂载和影响性能的全量备份可能是 R3。

执行前检查：

- 源数据一致性方法和应用官方备份流程。
- 目标空间、inode、配额、吞吐、网络和保留期。
- 备份窗口对 CPU、IO、锁和延迟的影响。
- 文件权限、ACL、xattr、hardlink、稀疏文件、设备文件和 SELinux context 是否需保留。
- 排除项是否会漏掉恢复必需的配置、证书、WAL/binlog 或元数据。
- 备份失败/中断后的清理与重试语义。

不要为赶进度把在线数据库数据目录直接打包并宣称为一致备份；使用该数据库支持的备份和恢复机制。

## 5. 完整性验证

验证至少分四层：

1. **作业层**：备份任务退出状态、日志、告警和完成时间。
2. **介质层**：对象/卷可读，清单、大小、校验和或工具 verify 通过。
3. **内容层**：关键文件、权限、schema、WAL/增量链和依赖齐全。
4. **恢复层**：在隔离环境实际恢复并完成应用一致性/业务校验。

只校验备份文件 hash 只能证明读取内容与记录一致，不能证明源数据当时一致或应用能启动。

验证命令优先使用备份工具的只读 list/check/verify 模式；不同工具语义不同，必须先查实际版本帮助和官方文档。

## 6. 恢复前门禁

恢复通常为 R3，原位覆盖尤其危险。执行前必须明确授权并满足：

- 恢复点、源备份、目标路径/设备/实例逐一核对。
- 目标当前数据已另行保护，或业务负责人明确接受覆盖。
- 恢复环境隔离，避免向真实用户发信、触发支付、任务、leader election 或外部回调。
- 目标容量、文件系统、软件版本、UID/GID、时区和依赖兼容。
- 加密密钥可用但不暴露，审计记录开启。
- 回退方案、停止条件和恢复后验证清单已就绪。

优先恢复到新路径、新卷或隔离实例，再切换流量；不要把未经验证的数据直接覆盖唯一生产副本。

## 7. 恢复执行纪律

- 一次只推进一个阶段：准备目标 → 恢复基础数据 → 应用增量/WAL → 一致性检查 → 只读验证 → 受控启用。
- 每阶段记录开始/结束时间、工具版本、恢复点、退出码和摘要。
- 输出与计划不符、增量链断裂、校验失败、版本不兼容或空间不足时立即停止。
- 不通过跳过校验、丢弃 journal/WAL、强制覆盖或忽略权限错误来“完成”恢复。
- 恢复期间避免源和目标同时对外写入；切换前明确谁是唯一写入方。

## 8. 恢复后验证

至少包括：

- 文件数量/大小、权限/ACL/xattr、关键摘要和时间范围。
- 数据库/应用自带一致性检查及 schema/version。
- 关键业务对象的抽样与边界时间数据。
- 服务启动、依赖、端口、后台任务和真实业务健康检查。
- 日志无新 corruption/error，资源和性能处于合理范围。
- RPO/RTO 实际值与预期差距。

验证通过前保持隔离或只读。技术启动成功不等于业务恢复成功，应由数据/业务所有者确认关键数据。

## 9. 切换与回退

切换流量、挂载、DNS、主从角色或写入端均为独立 R3：

- 切换前冻结或协调写入，避免双写和脑裂。
- 记录旧目标和 TTL/缓存/连接 draining 行为。
- 小流量 canary，监控错误率、延迟、数据写入和依赖。
- 定义回退触发阈值；回退前确认新数据如何处理，不能简单切回造成数据分叉。
- 旧环境保留到观察窗口结束，访问权限最小化，不立即销毁。

## 10. 演练与报告

定期演练应验证随机恢复点和完整链，而不是总用同一份样例。演练报告包含：

- 选取范围、恢复点、目标 RPO/RTO。
- 实际耗时、人工步骤、失败和绕行。
- 数据一致性与业务验收结果。
- 密钥、权限、容量、网络和文档缺口。
- 改进项、责任人和截止时间。

任何未做真实恢复验证的备份，最终报告必须明确标注“备份存在但可恢复性未经验证”。
